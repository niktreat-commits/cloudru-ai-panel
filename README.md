# Cloud.ru: подбор ИИ-решения на стенде

Готовый к запуску сервер Node.js и демонстрационный интерфейс 9:16 по макетам подрядчиков. В одном образе можно развернуть демо и API. При подключении отдельного фронта этот же образ можно запустить только как API.

Формулы и сценарии взяты из предыдущей версии. В примере тарифный снимок от **12.10.2026**, расчёт предварительный. Перед показом сверить `core/pricing.json` с утверждёнными тарифами. Готовые модели, GPU и дополнительные сервисы оцениваются в границах выбранного способа запуска.

## Запуск и проверка

Требуется Node.js 22 или новее. Зависимости устанавливать не нужно.

```sh
npm test
npm start
```

Открыть [http://localhost:8080](http://localhost:8080). Проверить в полноэкранном браузере на портретном экране 9:16. Проверка сервера: `GET /healthz`. Описание API: `GET /openapi.json`.

Чтобы собрать HTML для просмотра без сервера:

```sh
npm run preview:html
```

Открыть полученный `Cloudru-panel-preview.html` в браузере. В этом файле расчёт выполняется локально той же формулой. В демо по адресу сервера интерфейс вызывает API.

## Два метода для фронта

| Метод | Вход | Ответ |
| --- | --- | --- |
| `GET /api/catalog` | Без параметров | Отрасли, роли, задачи и их поля, модели, способы запуска, варианты размещения, таймер сброса |
| `POST /api/estimate` | Отрасль, роль, задача, размещение, параметры и настройки | Бюджет, нагрузка, варианты запуска, сервисы, допущения и следующий шаг |

Контракт: [openapi.json](openapi.json). Пример: [запрос](examples/estimate-request.json), [ответ](examples/estimate-response.json). Версия API: **1.0.0**.

### Как подключить к макетам

| Экран | Данные |
| --- | --- |
| 01. Отрасль | `catalog.industries` |
| 02. Роль | `catalog.roles`. Для подписи выбранной роли можно использовать `catalog.routes[industry + ':' + role].roleLabel` |
| 03. Задача | `route.recommendedTaskIds` для четырёх рекомендаций; `catalog.taskIds` для полного списка. В выбранном контексте поля задачи берём как `{ ...catalog.tasks[task], ...route.taskOverrides[task] }` |
| 04. Результат | Поля задачи — `fields`, стартовые значения — `defaults`. Бюджет — `budget`, нагрузка — `workload.stats`, рекомендации — `services`, сравнение запуска — `options` |
| Модель и допущения | `settingIds`, `settingFields`, `models`, `launchIds` для элементов управления; `workload.formula`, `workload.assumptions`, `budget.note`, `excluded`, `pricing.snapshotDate` для пояснения |
| Кнопка регистрации | Вызывает форму или сервис подрядчика; у расчётного API нет метода регистрации |

1. Загружайте каталог один раз. Названия, разрешённые поля и их значения берите из каталога. Идентификаторы не заменяйте подписями на экране.
2. Сразу после выбора задачи подставьте её `defaults` и запросите первый расчёт. При редактировании числа запрашивайте результат после паузы около 300 мс. При быстром вводе отменяйте предыдущий запрос и показывайте только последний ответ.
3. `values` содержат поля конкретной задачи, `settings` — дополнительные настройки из `settingIds`. Числа отправляйте числами, галочки — `true` или `false`. Пропущенные параметры получают значения по умолчанию. Для выбора способа запуска передайте ID в `settings.launch`.
4. При `budget.status === 'ready'` показывайте сумму `budget.amountRub`, её период и состав оценки. `null` — цена пока не рассчитана. Статусы `benchmark`, `training`, `blocked`, `placement` и `custom` сопровождайте текстом из `budget.note`. `options[].available === false` означает, что вариант пока нельзя выбрать. Покажите причину из `reason`.
5. При ошибке оставляйте введённые параметры и давайте повторить запрос. Если отображаете предыдущий результат, помечайте его как обновляемый. При `400 INVALID_INPUT` используйте `field` и `message`, чтобы подсказать, что поправить.
6. Через 45 секунд бездействия очистите выбор и верните стартовый экран. Предупреждение — через 35 секунд. У подрядчика должен быть свой сброс открытой формы и её полей.

Тестовый запрос после запуска:

```sh
curl -fsS http://localhost:8080/api/estimate \
  -H 'Content-Type: application/json' \
  --data-binary @examples/estimate-request.json
```

## Регистрация

Расчётный сервер не сохраняет сессии, заявки и контакты. В нём нет подключения S3 и генерации документов. API принимает только параметры расчёта.

В демонстрационном фронте кнопка создаёт событие `cloudru:contact-request`. `event.detail.selection` — параметры, `event.detail.estimate` — результат. Интегратор может отменить заглушку через `event.preventDefault()` и открыть свою форму. Пример для отдельного JS-файла:

```js
window.addEventListener('cloudru:contact-request', event => {
  event.preventDefault();
  // Открыть вашу форму. При необходимости связать регистрацию с расчётом:
  // openRegistration(event.detail.selection, event.detail.estimate);
});
// После подтверждённой регистрации показать благодарность и вернуть старт:
// window.dispatchEvent(new Event('cloudru:reset'));
```

Если в референсный фронт встраивается внешняя форма или запрос к внешнему сервису, разрешите её точный адрес в политике Content Security Policy. Если подрядчики реализуют свой фронт, им достаточно API-контракта. Они могут использовать обычный обработчик кнопки. Не показывайте сообщение об успешной регистрации до ответа их системы. Контакты в `/api/estimate` не отправляются.

## Развёртывание в Container Apps

Рабочая ветка — **`main`**. Распакуйте содержимое архива в корень репозитория. Замените файлы приложения, в том числе всю папку `server/`, и удалите файлы старого приложения, которых нет в новом комплекте. Сохраните настройки репозитория и файлы пайплайна. Сделайте один коммит с обновлением в `main`.

В Workflow Studio соберите образ из `main`: контекст — корень репозитория, файл — `Dockerfile`. Отдельный шаг `npm ci` для этого приложения не нужен. Dockerfile сам запускает `node server/index.mjs`.

1. Из Artifact Registry возьмите URI вашего образа. Добавьте собственный тег версии. Пример значения: `<ваш-реестр>.cr.cloud.ru/cloudru-panel-api:v1`.
2. Соберите и отправьте образ через ваш пайплайн. Для ручной сборки после входа в существующий реестр:

   ```sh
   PANEL_IMAGE='<ваш-реестр>.cr.cloud.ru/cloudru-panel-api:v1'
   docker build --platform linux/amd64 -t "$PANEL_IMAGE" .
   docker push "$PANEL_IMAGE"
   ```

3. В текущем Container App создайте ревизию с загруженным образом. Порт **8080**, HTTP-проверка **/healthz**. Команду запуска оставьте из образа. Для просмотра по ссылке включите HTTPS-адрес. Для работы на стенде оставьте минимум один экземпляр, чтобы первый расчёт не ждал запуска контейнера.
4. Откройте HTTPS-адрес тестового приложения. Проверьте стартовый экран и расчёт из примера на `/api/estimate`. Передайте коллегам базовый HTTPS-адрес и `openapi.json`.
5. При размещении фронта на другом домене добавьте его полный origin в `FRONTEND_ORIGINS`, без пути и завершающего слеша. Для нескольких адресов используйте запятые: `https://panel.example.test,http://localhost:5173`. Это разрешение для браузера. Ключи API в браузер не требуются. Если компании нужен закрытый тестовый контур, доступ ограничивается настройками сети или шлюзом.
6. По умолчанию в контейнере работает и демо, и API. Чтобы оставить только API, задайте `SERVE_DEMO=false`. На расчёте, каталоге и проверке сервера эта настройка не сказывается.

**Кто держит домен.** Домен определяется местом размещения и настройками DNS. Подрядчики могут передать сборку фронта и разместить её вместе с нашим API на адресе Cloud.ru. Если они размещают фронт отдельно, наш API сохраняет свой адрес, а адрес фронта добавляется в список разрешённых.

**Что передать подрядчикам.** HTTPS-адрес приложения, `openapi.json` и ссылку на репозиторий с веткой `main`. Если они будут коммитить, дайте доступ на запись. Их зона изменений — `public/` и подключение формы. Перед коммитом запускайте `npm test`, а время обновления панели согласуйте с владельцем пайплайна: если настроен запуск от push, сборка начнётся после коммита.

Шрифты входят в `public/fonts.css`: SB Sans Display и SB Sans Text, начертания Regular и SemiBold. Они уже встроены в автономное HTML-демо.
