# Обновление через GitHub и Workflow Studio

Приложение остаётся в вашем Container Apps. В этой версии появился сервер, поэтому нужен новый образ по Dockerfile из архива.

## 1. Обновите репозиторий

1. Распакуйте архив на компьютере.
2. Загрузите **содержимое** папки `cloudru-ai-panel-containerapps` в корень вашего GitHub-репозитория: `Dockerfile`, `package.json`, `package-lock.json`, папки `dist`, `server`, `config`, `scripts`, `tests` и документы.
3. Удалите старый `nginx.conf`. Новый Dockerfile запускает Node.js на том же порту 8080.
4. Убедитесь, что `dist` загружен целиком, включая `fonts.css`, `catalog.mjs`, `specification.mjs` и `session-client.mjs`.
5. Не загружайте заполненный `.env`, ключи, `node_modules`, выгрузки и реальные контакты. `.env.example` — только пример, его можно хранить в репозитории.
6. Сделайте commit в ветку, из которой собирается ваш workflow.

Если используете Git в терминале, сначала проверьте список файлов через `git status`, затем добавляйте только код и пустой пример конфигурации. Заполненный `.env` исключён из Git.

## 2. Добавьте настройки в Container Apps

В настройках приложения/новой ревизии задайте переменные окружения. Если Workflow Studio у вас подставляет их в манифест при развёртывании, используйте его существующий механизм секретов.

| Имя | Что указать |
| --- | --- |
| `S3_BUCKET` | `cloudru-aij-leads` |
| `S3_ENDPOINT` | `https://s3.cloud.ru` |
| `AWS_REGION` | `ru-central-1` |
| `AWS_ACCESS_KEY_ID` | Tenant ID, двоеточие, Key ID сервисного аккаунта |
| `AWS_SECRET_ACCESS_KEY` | Key Secret сервисного аккаунта |
| `SESSION_SECRET` | Новый случайный секрет, минимум 32 символа; одинаковый для всех реплик |
| `PUBLIC_ORIGIN` | `https://appazn4y6uhi3i6pr4rve0dv8ayi.containerapps.ru` |
| `EVENT_ID` | `aij-2026` |
| `KIOSK_ID` | `stand-1` либо номер панели |
| `PORT` | `8080` |
| `LEGAL_APPROVED` | Сначала `false`; `true` после внутреннего согласования `config/legal.json` |

Храните Key Secret и SESSION_SECRET как секреты. Ключ доступа тоже лучше передавать из закрытой конфигурации. **Не используйте Docker build arguments или переменные фронтенд-сборки для ключей.** Все значения нужны контейнеру во время запуска.

Задаётся имя бакета, не его внутренний ID. Tenant ID нужен только в составном идентификаторе ключа. Endpoint остаётся без имени бакета.

## 3. Настройте бакет

Бакет уже создан. Оставьте его приватным. Сервисному аккаунту нужны чтение, запись, просмотр объектов и удаление заданий в этом бакете. Не делайте публичный веб-сайт или CORS для браузера: с S3 общается сервер.

После согласования сроков настройте жизненный цикл для `sessions/`, `leads/` и `jobs/` по README. Сроки в приложении не заменяют правила удаления в S3.

## 4. Запустите ваш workflow

В существующем workflow сохраните привычные шаги checkout GitHub → сборка образа → Container Registry → Container Apps. Измените только то, что требуется новой версии:

- Контекст сборки — корень репозитория, Dockerfile — `/Dockerfile` в этом контексте.
- Собирается новый образ с Node.js; используйте новый тег, связанный с commit, чтобы загрузилась новая версия.
- Контейнер слушает `0.0.0.0:8080`.
- Команду запуска можно оставить из Dockerfile. Если в настройках оставалась команда nginx, удалите её.
- Не заменяйте Dockerfile шагом «статический сайт»: серверные маршруты `/api/` обязательны.
- Для постоянной генерации DOCX держите минимум одну реплику. Данные не хранятся на диске контейнера, общий том не нужен.
- Liveness: `/healthz`; доступ к хранилищу отдельно проверяется `/readyz`.

Названия элементов Workflow Studio зависят от вашего workflow. Готовый Dockerfile и переменные выше не требуют привязки к отдельному шаблону студии.

## 5. Проверьте новую ревизию

1. Откройте приложение по вашему HTTPS-адресу и пройдите подбор. Расчёт должен появиться сразу, без заполнения контактов.
2. Убедитесь, что внизу отображается «Выбор сохранён». В `sessions/` должны появиться JSON-снимки без контактов.
3. Оставьте панель: на 35-й секунде должно появиться предупреждение, на 45-й — начальный экран.
4. После согласования текста включите `LEGAL_APPROVED=true` и перезапустите/создайте новую ревизию с этой переменной.
5. Отправьте одну заявку с тестовыми данными, не используя реального человека. Без телефона и согласия отправка не допускается.
6. После успешной записи появится благодарность, через пять секунд — начальный экран. В `leads/.../lead.json` проверьте контакты, задачу, спецификацию и согласие.
7. В течение следующего цикла обработчика появится `card.docx` (обычно после 15 секунд, при очереди позже). Скачайте его из приватной консоли и проверьте. Задание в `jobs/` после этого исчезнет.
8. Удалите тестовую заявку, её документ и связанную сессию по внутренней процедуре. Подготовка реальных писем после конференции остаётся за командой — приложение их автоматически не отправляет.

Для отдельной проверки доступа выполните `scripts/check-storage.mjs` с окружением контейнера или локальным `.env`. Скрипт не выводит ключи и не использует контакты.

## Если не сохраняется

- `SignatureDoesNotMatch` / `InvalidAccessKeyId`: проверьте формат `tenant_id:key_id`, Key Secret, регион и часы окружения. Tenant ID берётся в Object Storage → Параметры работы с API.
- `AccessDenied`: проверьте права сервисного аккаунта именно на `cloudru-aij-leads`, включая чтение/просмотр/удаление.
- Форма отключена: проверьте ключи, `SESSION_SECRET` длиной не менее 32 символов, точный `PUBLIC_ORIGIN` без `/` в конце и `LEGAL_APPROVED=true`.
- Ошибка источника запроса: `PUBLIC_ORIGIN` должен совпадать с адресом в браузере, включая `https://` и нестандартный порт, если он есть.
- `lead.json` есть, а DOCX нет: проверьте, что реплика работает и права позволяют читать `jobs/` и удалять обработанные задания; затем запустите `scripts/retry-documents.mjs`.
- В браузере остаётся старый вид: обновите страницу с очисткой кеша и проверьте, что новая ревизия использует новый тег образа.

Ключи и реальные карточки не отправляйте в чат и не прикладывайте к GitHub Issues.
